# Application Review & Remediation Plan

**Date:** 2026-06-11
**Scope:** Full-application audit — data integrity, scoring logic, displays, pipeline, links, and content sourcing.
**Goal:** Make this a trustworthy source for accountability of elected representatives.

---

## 1. What the application is

A statically-exported Next.js 16 site (Cloudflare Pages) that tracks all three branches of
government:

- **Legislative** — 538 member profiles with voting records, campaign finance, stock trades,
  committee conflicts, and a "Say vs. Do" alignment score comparing stated positions
  (OnTheIssues) to actual roll-call votes.
- **Executive** — President/VP/Cabinet profiles, promise tracking, executive orders, conflicts
  of interest, DOGE tracker, agency spending (USASpending).
- **Judicial** — SCOTUS justice profiles and ideology scores.

Data is JSON files in `src/data/` baked into the static build, refreshed by GitHub Actions
(daily vote/EO/news syncs, weekly data refresh).

**Build health:** `pnpm build` passes; all 730 tests pass. The problems are not code breakage —
they are data integrity, scoring correctness, and trust/presentation problems.

---

## 2. Findings

### P0 — Trust-breaking issues (the site says things that are wrong)

#### P0.1 The core "Say vs. Do" alignment score is generated by a methodology the repo itself calls broken
- The shipped `src/data/alignment-scores.json` (254 members) was generated by the **old v2
  pipeline** (`scripts/calculate-alignment.ts`). Records have the v2 shape (`expected_vote`,
  no `say_vs_do_v3` field).
- The v2 script is now **unrunnable** — it imports `../src/lib/alignment.js`, which was deleted.
- A **v3 rewrite exists** (`scripts/compute-scores.ts` + `src/lib/say-vs-do.ts`) whose header
  explicitly says v2 was "broken … causing the algorithm to invert alignment for the majority
  of data" — but **nothing ever runs it**: it is not in `package.json` prebuild, not in any
  workflow.
- Root cause of the v2 inversion, still visible in shipped data: every key vote in
  `key-votes.json` has `publicBenefit: null`, and v2 defaulted that to `'positive'`
  (`scripts/calculate-alignment.ts:96`), then treated any stance containing "supports" as
  progressive (`:170-179`). So "Supports privatize Social Security" was scored as a
  *progressive* stance, producing the documented contradictions (e.g., reps with 99% party
  loyalty showing 1-2% scores; consistent conservatives flagged as "contradictions").
- This was independently documented in `QA-UX-REVIEW-2026-02-13.md` as the #1 critical issue
  and is still what users see today.
- Category breakdowns also confuse: category totals sum to more than `total_votes_analyzed`
  because one roll call maps to multiple position topics, with no explanation.

#### P0.2 Fabricated source citations (`example.com`)
- `src/data/presidential-promises.json` — **20** `https://example.com/...` source URLs
  presented as citations (e.g., promises citing "https://example.com/campaign-speech").
- `src/data/executive-actions.json` — **9** sources naming real publications ("Defense News",
  etc.) but linking to `https://example.com`. Displayed on `/executive/timeline`
  (`src/app/executive/timeline/page.tsx:5`) and cabinet alignment sections
  (`src/app/executive/cabinet/[role]/alignment-section.tsx:4`).
- For a site whose pitch is "facts you can verify," unverifiable citations are disqualifying.

#### P0.3 Stock trade stats contradict the trade table
- `src/components/StockTradesSection.tsx:36-41`: `isSale()` matches only the exact string
  `"sale"`. The data (`trades-by-member.json`) contains **3,431 "Sale (Full)"** and
  **2,229 "Sale (Partial)"** transactions that are silently excluded from the Sales count,
  plus **628 "Exchange"** trades counted in neither bucket.
- Result (reported in the Feb QA review, still live): headers like "23 trades, 15 purchases,
  0 sales" above a table visibly showing sale rows. Purchases + Sales ≠ Total with no
  explanation.

#### P0.4 Published methodology doesn't match the code
- `/methodology` page (`src/app/methodology/page.tsx:127-175`) documents factor weights
  **50% / 20% / 15% / 15%**.
- The code (`src/lib/alignment-enhanced.ts:225-264`) actually uses **60/15/15/10**
  (or 65/20/15 when bipartisan data is missing).
- Users following the published methodology cannot reproduce the scores — the exact failure
  mode that destroys trust in a transparency site.

#### P0.5 Executive-branch spending tracking has never worked
- `src/data/usaspending-sync-status.json`: `status: "error"`, `last_success_at: null`, all
  counters zero. `usaspending.json` is an empty shell. The weekly `usaspending-sync.yml`
  workflow has never produced data, so agency budget/spending features render from nothing.

#### P0.6 Live vote sync is House-only
- `src/data/vote-sync-status.json`: nightly sync ends `"partial"` with
  `senate-list: Congress API error: 404 Not Found` — Senate roll calls are missing from
  "live" vote data, with no user-facing indication. Also `total_roll_calls_fetched: 0` vs
  `total_roll_calls_stored: 7` — the status metrics themselves are inconsistent.

### P1 — Stale and hardcoded data presented as current

#### P1.1 Orphaned data files (no script or workflow ever regenerates them)
`affected-programs.json`, `budget-impacts.json`, `cabinet-spending.json`,
`committee-conflicts.json`, `constituent-preferences.json` (generated 2025-12-01),
`deep-dives.json`, `executive-actions.json`, `leadership-scrutiny.json`,
`policy-impacts.json`, `presidential-promises.json`, `scandals.json` (timestamps frozen at
2024-02-11), `scotus.json`, `top-captured.json`, `trump-approval.json`, `trump-conflicts.json`,
`vp.json`. These will go permanently stale with no warning to users or maintainers.

#### P1.2 Data that claims to be fresh but isn't
- **Trump approval** (`trump-approval.json`): frozen at `last_updated: 2026-03-11` — 3 months
  stale — while `ApprovalRatingCard.tsx:123` tells users data is "updated weekly."
- **Top captured panel** (`TopCapturedPanel.tsx:128`): labeled "FEC 2022 cycle" while
  `finance.json` is on the 2026 cycle.
- **Site banner** (`DevelopmentBanner.tsx`) shows "Data synced <date>" from the vote-sync
  status only — it reads as a whole-site freshness claim while most datasets are months old.

#### P1.3 Hardcoded homepage editorial stats (`src/app/page.tsx`)
The hero/spotlight content is all hardcoded constants: leadership spotlight numbers
("Broke from his own party 9 times in 189 votes", "40.7% of her $2.7M", "19.4% PAC-funded"),
top-donor-sector bar charts, and `SITE_STATS` ("81K+ votes analyzed", "66 reps breaking with
their party", "26 executive officials — Updated daily"). None are computed from the data; all
silently drift from reality.

#### P1.4 Questionable finance figures
- `finance.json` `top_contributors` mixes scripted output (only 7 hardcoded leadership
  committees, cycle hardcoded to 2024 in `pipeline/update-top-contributors.ts:13`) with
  entries like "Senate Leadership Fund (own Super PAC) — $84,000,000" presented as if it were
  a contribution to the member's campaign — that's a Super PAC's own raising, not a
  contribution, and FEC rules make the framing misleading.
- `cabinet.json` includes net-worth ranges with no source for any of the 16 entries.

#### P1.5 Coverage gaps presented without explanation
- Members: 538. With positions: 270. With alignment score: 254. With finance: 472.
- Bill plain-English summaries: 67 bills (`bill-summaries.json`) vs ~95+ shown on `/bills`.
- Pages render for everyone, so roughly half of all member pages show empty/missing core
  sections with no "why" or coverage statement.

### P2 — Confusing or misleading displays

1. **Approval bars don't sum to 100%** — 42.8% approve + 55.6% disapprove with no
   "unsure" segment; side-by-side bars imply a complete whole
   (`ApprovalRatingCard.tsx:52-114`).
2. **Finance factor math** (`alignment-enhanced.ts:125-134`) — small-donor bonus can push the
   pre-clamp score over 100; double-counts small donors against PAC/large-donor shares.
3. **Bipartisan factor paradox** (`alignment-enhanced.ts:172-193`) — >90% party loyalty is
   *penalized* yet a 95% loyalist still scores 90/100 labeled "Strictly follows party line";
   sub-75% loyalty is also penalized. The "sweet spot" (75-90%) is an undisclosed editorial
   judgment baked into a "score."
4. **Verdict badges** ("DONOR CAPTURED", "MIXED ALLEGIANCE" — `RepVerdictBadge.tsx:20-30`)
   trigger on undocumented thresholds (≥2 high conflicts, PAC ≥ 60%); no tooltip/legend.
5. **Conflict severity** thresholds ($100K/$50K — `conflict-detector.ts:149-155`) undocumented.
6. **Party loyalty chart** buckets are uneven widths (5% and 10%) — visually misleading
   (`PartyLoyaltyChart.tsx:23-32`).
7. **Category breakdown totals** exceed the analyzed-vote total (multi-topic counting, see
   P0.1) with no footnote.
8. **No "as of" dates on most data sections**; no color/badge legend anywhere (red = Republican
   in one place, red = "bad" in another).
9. **Bills page jargon** — most bills display raw legislative titles ("Providing for
   consideration of the bill (H.R. 7148)…"); the CRS/AI summary file covers only 67 bills.
10. **DW-NOMINATE / "Ideology score 0.72"** shown without axis explanation for lay users
    (`IdeologySpectrumChart.tsx:89-125`).

### P3 — Dead code, broken scripts, repo hygiene

1. `scripts/calculate-alignment.ts` — broken import (`src/lib/alignment.js` deleted); should be
   removed so no one regenerates bad data with it.
2. `pipeline/sources/propublica-votes.ts` — dead code, hardcoded Congress 118; ProPublica's
   Congress API is defunct. The `pipeline:votes` npm script still points at it. README still
   lists ProPublica as a primary data source.
3. `src/data/news-cache.json` missing locally (README says build expects it; fine if CI
   generates it, but the static build silently ships without news if absent).
4. Navigation labels `/judicial/supreme-court` "Coming Soon" but it redirects to a fully
   functional `/judicial/scotus` (`Navigation.tsx:38`).
5. Repo root contains ~25 stale task/summary markdown files (TASK-*, ISSUE-*, *-COMPLETE.md)
   that obscure the real docs.
6. `scotus.json.backup` checked into `src/data/`.
7. `/congress` page calls `https://ipapi.co/json/` client-side for geolocation — a third-party
   PII call worth disclosing in the privacy policy (or removing).

## 3. Remediation plan

### Phase 0 — Stop saying wrong things (1-2 days of work, do first)

| # | Action | Files |
|---|--------|-------|
| 0.1 | Regenerate alignment data with v3 (`compute-scores.ts`), verify spot-checks against known members (e.g., high-loyalty Republicans should no longer score 0-2%), and wire it into `prebuild` + weekly refresh workflow | `scripts/compute-scores.ts`, `package.json`, `.github/workflows/weekly-data-refresh.yml` |
| 0.2 | Delete broken v2 script + dead ProPublica votes source + `pipeline:votes` script; remove ProPublica from README data sources | `scripts/calculate-alignment.ts`, `pipeline/sources/propublica-votes.ts`, `package.json`, `README.md` |
| 0.3 | Fix trade type counting: count `Sale (Full)`/`Sale (Partial)` as sales, add an "Other/Exchange" stat so Purchases + Sales + Other = Total | `src/components/StockTradesSection.tsx` |
| 0.4 | Fix `/methodology` to match actual code weights (or change code to match docs — pick one source of truth and add a test asserting they agree) | `src/app/methodology/page.tsx`, `src/lib/alignment-enhanced.ts` |
| 0.5 | Remove or re-source every `example.com` citation. Default: hide entries lacking a real source behind a build-time filter; restore them as sources are verified | `src/data/presidential-promises.json`, `src/data/executive-actions.json` |
| 0.6 | Fix the "updated weekly" copy on approval card; show actual `last_updated` and a staleness warning when > 14 days old | `src/components/ApprovalRatingCard.tsx` |
| 0.7 | Fix TopCapturedPanel cycle label to read from data, not hardcoded "2022 cycle" | `src/components/TopCapturedPanel.tsx:128` |

### Phase 2 — Make the numbers understandable (1-2 weeks, parallelizable with Phase 1)

1. **One-line plain-English explanation + tooltip on every score** (alignment, donor capture,
   party loyalty, ideology, verdict badges), with "higher/lower means…", the denominator
   ("based on N votes"), and a link to methodology.
2. **Show confidence prominently** — v3 already computes
   high/medium/low/insufficient; gate score display on it (insufficient → show "Not enough
   data to score" instead of a number).
3. **Document every threshold** in `/methodology`: verdict badge triggers, conflict severity
   dollar bands, time-decay weights, minimum-vote threshold, bipartisan "sweet spot" — and add
   tests asserting docs match constants.
4. **Fix the small-donor double-count** in the finance factor and the bipartisan
   score/label mismatch (P2.2, P2.3).
5. **Approval card**: add the undecided remainder so segments sum to 100%.
6. **Color/badge legend** component used site-wide; stop using red for both party and "bad".
7. **Party loyalty chart**: uniform buckets.
8. **Bills**: extend `fetch-bill-summaries.ts` coverage to all displayed bills; show CRS/AI
   plain-English summary first, official title second; label AI-generated summaries as such.
9. **Coverage statements** on list pages: "Alignment scores available for 254 of 538 members
   (those with published OnTheIssues positions)."

### Phase 3 — Keep it trustworthy (ongoing)

1. **CI guard tests**: no `example.com` URLs in `src/data/`; every data file has `_meta`;
   methodology constants match docs; schema validation per data file; freshness check that
   fails the weekly workflow if auto-refreshed files exceed SLA.
2. **Workflow alerting**: vote/EO/news/usaspending syncs open a GitHub issue on failure
   instead of writing a "partial" status nobody reads.
3. **Repo cleanup**: move the ~25 TASK-*/ISSUE-* markdown files to `docs/archive/`; delete
   `scotus.json.backup`; fix the Supreme Court "Coming Soon" nav badge; document or remove the
   `ipapi.co` geolocation call.
4. **Editorial content policy**: deep-dives/DOGE/scandals pages get a visible "Editorial —
   last reviewed <date>" header distinguishing curated narrative from pipeline data.

## 4. Decision points (need owner input)

1. **Alignment scores in the interim** — Regenerate with v3 immediately and ship with
   clear confidence labels (recommended), or hide the score site-wide until the v3 output has
   been manually validated against a sample of members?
2. **Fabricated-source content** — Hide promises/actions whose only source is `example.com`
   until re-sourced (recommended), or keep them visible with a "source pending verification"
   label?
3. **Orphaned editorial datasets** (scandals, deep-dives, trump-approval, constituent
   preferences, scotus, cabinet net worth) — invest in automated refresh, keep as dated
   editorial content, or cut the features that depend on them? Approval ratings and
   constituent preferences in particular are poll data that arguably shouldn't be shown
   at all if it can't be kept current.
4. **USASpending features** — fix the pipeline or remove the agency-spending UI for now?

---

## 5. Suggested sequencing

```
Week 1:   Phase 0 (all items) + 1.1 (Senate votes) + decision points resolved
Week 2-3: Phase 1 (plumbing, provenance, staleness) + Phase 2 items 1-5
Week 4:   Phase 2 items 6-9 + Phase 3 CI guards + cleanup
Ongoing:  Phase 3 alerting + editorial review cadence
```

The single highest-leverage change is **0.1 + 0.4 + 1.4 together**: a correct score, a
methodology page that matches it, and an "as of" date on everything. That combination is what
makes the site defensible when someone challenges a number — which, for an accountability
site, is the whole game.
